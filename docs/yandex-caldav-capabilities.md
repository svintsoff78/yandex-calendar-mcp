# Что на самом деле умеет CalDAV Яндекса

Проверено 18 сентября 2026 года на живом аккаунте. Все выводы получены
запросами из задачи 1 плана, а не из документации.

## OPTIONS /

```
HTTP/1.1 200 OK
DAV: 1,addressbook,calendar-access,calendar-auto-schedule,calendar-availability,
     calendar-schedule,calendar-proxy,calendarserver-private-comments,
     calendarserver-principal-property-search
Allow: OPTIONS, GET, HEAD, POST, TRACE, PROPFIND, PROPPATCH, MKCOL, COPY, PUT,
       DELETE, MOVE, LOCK, UNLOCK, REPORT, MKCALENDAR
```

Сервер объявляет заметно больше, чем предполагалось при проектировании:
планирование (`calendar-auto-schedule`, `calendar-schedule`) и доступность
(`calendar-availability`) заявлены, а не отсутствуют.

## Обнаружение

| Шаг | Результат |
|---|---|
| `PROPFIND /` | `/principals/users/<логин с %40>/` |
| `PROPFIND <principal>` | `/calendars/<логин с %40>/` |
| `PROPFIND <home>` Depth 1 | 6 коллекций |

Из шести коллекций календарями являются три; остальные — корень дома,
`inbox` и `outbox`. Наличие `schedule-inbox` и `schedule-outbox`
подтверждает поддержку планирования по RFC 6638 на уровне коллекций.

Один из трёх календарей — список задач (`supported-calendar-component-set`
содержит VTODO, а не VEVENT). Его нужно отфильтровывать, иначе он попадёт
в выдачу инструментов пустым.

## Что подтвердилось

- `calendar-query` с фильтром по VEVENT и диапазону времени работает.
- VTIMEZONE приходит вложенным прямо в `calendar-data` каждого события.
- Повторяющиеся события отдаются одним объектом с RRULE.
- События несут ORGANIZER, ATTENDEE с PARTSTAT, CONFERENCE и
  `X-TELEMOST-CONFERENCE`.

## Что опровергнуто

| Ожидание при проектировании | Факт |
|---|---|
| Серверное раскрытие повторов под вопросом | `<C:expand>` **игнорируется**: ответ побайтово тот же, RRULE не тронут. Локальное раскрытие обязательно |
| Свойство `calendar-timezone` доступно | Возвращается со статусом **404** для всех коллекций. Запасного источника VTIMEZONE через это свойство нет, база IANA обязательна |
| Планирование скорее всего отсутствует | Объявлено в DAV и подкреплено коллекциями inbox/outbox |

## Особенности, влияющие на код

1. **ETag без кавычек.** Яндекс отдаёт голое число — метку времени в
   миллисекундах, например `1789383239000`. Условные заголовки должны
   передавать значение как есть, не добавляя и не снимая кавычки.

2. **Имя файла объекта не выводится из UID.** UID вида
   `aaaabbbbccccdddd11@yandex.ru` соответствует объекту
   `aaaabbbbccccdddd11yandex.ru.ics` — собака выброшена, а не закодирована.
   Восстанавливать путь из UID нельзя: для чужих событий он не совпадёт.
   Путь берётся из `href` ответа на `calendar-query`.

3. **Пространства имён смешаны.** В одном и том же ответе `href` и `status`
   идут без префикса с явным `xmlns="DAV:"`, а свойства — с префиксом `D:`.
   Разбор со снятием префиксов это переживает, ручной разбор по именам
   тегов — нет.

## Живая сверка поведения записи (19 сентября 2026)

Проверено на временном календаре, созданном в аккаунте с согласия
пользователя и удалённом после проверки. Участники в пробах не
использовались, писем никому не уходило. Проверки, требующие действий
в веб-интерфейсе Яндекса и рассылки приглашений, не выполнялись и
остаются рисками.

| № | Факт | Правило для кода |
|---|---|---|
| Ж1 | `MKCALENDAR` игнорирует запрошенный путь: календарь создаётся по адресу, выбранному сервером (`events-NNNNNNNN/`), ответ 201 | Сервер календари не создаёт; для тестов адрес нового календаря искать по имени |
| Ж2 | Порядок компонентов нормализуется: основной компонент серии всегда ставится первым, даже если прислан после переопределения | Основной компонент всё равно искать по отсутствию `RECURRENCE-ID`, а не по позиции: другие клиенты и старые записи могут отличаться |
| Ж3 | Объект из одного переопределения без основного компонента принимается и хранится | Чтение обязано такие объекты показывать |
| Ж4 | `RECURRENCE-ID;VALUE=DATE` и `EXDATE;VALUE=DATE` у серий на весь день принимаются и хранятся как есть | Для серий на весь день писать их именно так, а не DATE-TIME в UTC |
| Ж5 | RRULE переписывается: части переставляются, добавляется `INTERVAL=1`, у WEEKLY добавляется `BYDAY` из даты начала, `COUNT` может превратиться в `UNTIL` | Сравнивать правила только по смыслу — по раскрытым слотам, никогда по тексту. Код обязан принимать и `COUNT`, и `UNTIL` на чтении после собственной записи |
| Ж6 | `BYSETPOS` не поддерживается: правило «последний рабочий день месяца» молча записано как «последний четверг месяца», `WKST` выброшен | Правила с `BYSETPOS` и `WKST` не записывать: отказ с понятным текстом. После каждой записи правила — сверка раскрытых слотов с ожидаемыми |
| Ж7 | Пользовательские свойства `X-…` вырезаются целиком | На собственные служебные пометки в событии опираться нельзя |
| Ж8 | `CATEGORIES` перезаписываются именем календаря | Категории не показывать как пользовательские данные и не пытаться сохранить |
| Ж9 | Сервер сам добавляет `ORGANIZER` (владелец аккаунта), `CREATED`, `LAST-MODIFIED`, `CLASS`, `URL`, `CALSCALE`, `METHOD` | Собственные события считаются организованными владельцем аккаунта: `ORGANIZER`, равный логину, — не «чужой организатор» |
| Ж10 | Вложенный `VTIMEZONE` заменяется полным историческим описанием пояса от сервера | Не сравнивать `VTIMEZONE` по тексту |
| Ж11 | `SEQUENCE` хранится как прислан и сервером не увеличивается | Увеличивать `SEQUENCE` — ответственность клиента |
| Ж12 | ETag меняется при каждой записи, даже если текст объекта тот же | Равенство ETag нельзя использовать как «ничего не изменилось»; при неизвестном исходе записи сверять содержимое по смыслу |
| Ж13 | **`If-None-Match: *` не соблюдается**: запись поверх существующего объекта проходит с ответом 201 | Создание не защищено сервером. Для случайных UID это безопасно. Для детерминированных UID (продолжение серии) — перед созданием читать, не существует ли объект |
| Ж14 | `If-Match` на `PUT` соблюдается: несовпадение даёт 412 | Защита правки от одновременных изменений работает |
| Ж15 | **`If-Match` на `DELETE` не соблюдается**: удаление с заведомо устаревшим ETag прошло с ответом 204 | Перед удалением сервер обязан сам перечитать объект и сравнить ETag; остаётся узкое окно гонки между чтением и удалением |
| Ж16 | `PUT` с `If-Match` по несуществующему объекту создаёт его с ответом 201 вместо 412 | Правка объекта, удалённого параллельно, может его воскресить; окно узкое, объект перед правкой всё равно перечитывается |
| Ж17 | `calendar-query` по окну времени учитывает переопределения: встреча, перенесённая внутрь окна, возвращается; окно исходного слота перенесённой встречи объект не возвращает | Серверному фильтру по времени можно доверять для отбора объектов; раскрытие по-прежнему локальное |
| Ж18 | Имена файлов, заданные клиентом при создании, сохраняются | Для своих объектов путь по UID предсказуем; для чужих — только от сервера |
